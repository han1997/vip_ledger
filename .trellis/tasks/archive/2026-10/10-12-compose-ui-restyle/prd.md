# 按原型实现 Compose UI 整体改版（墨绿金 · 静奢记账）

## Goal

将现有 Compose UI 的视觉与交互整体切换到已确认的 HTML 原型基准
（`docs/ui-prototype/`，墨绿金 · 静奢记账方向）：暖象牙纸感底 + 深墨绿主色 +
黄铜金点缀、衬线金额数字、克制发丝边框卡片、记一笔一屏零滑动。
**不删除任何现有功能**，只做视觉与信息层级的重排；涉及新能力（如账户卡号）时
按 `ui-contract.md` 单独确认后再动 schema。

## What I already know

### 原型侧

- 原型当前版本 **v2.1**（`BASELINE.md`），状态**待用户确认**；v1.3 / v1.4 已确认但被后续版本取代。
  按 `ui-contract.md` 第 1 条，**只有已确认版本可作为实现依据** → 实现前必须先确认基准。
- 设计方向：墨绿主色 `#1A3C34`、深墨绿 `#0F2A24`、黄铜金 `#B08D57`、支出赭红 `#B23A2E`、
  收入松绿 `#2E7D5B`、转账靛蓝 `#3B5B7A`、纸感底 `#F7F5F0`、主文字 `#16211D`、发丝线 `#E6E1D6`。
- 排版：展示与金额用衬线体 + `tabular-nums` 等宽数字右对齐；正文无衬线。
- 间距 4pt 网格（4/8/12/16/20/24/32），圆角 8/12/16/20，触控 ≥44px —— 与现有
  `VipLedgerTokens` 可直接映射。
- 原型内已含完整页面集：首页 / 日历 / 资产 / 统计 / 我的 五 Tab + 记一笔 +
  账户详情子页 + 全部「我的」二级子页（账本/分类/标签/计划/AI/数据）+
  底部弹层选择器（账户/日期时间/标签）。
- 原型硬性规则：无假按钮、页面不跳出手机壳、无浏览器弹窗（对应 Compose：无死按钮、
  子页走导航、弹层用 ModalBottomSheet）。
- 原型「Compose 迁移映射」弹层已给出 token → 现状 Compose 的逐项迁移动作。

### 现有 App 侧

- 已是 Compose 全量 UI：五 Tab（`VipLedgerApp.kt`）+ 约 25 个 ledger 屏 +
  stats（统计/搜索/下钻）+ backup + ai 屏；`core:designsystem` 已有
  `VipLedgerTokens`、`GroupCard`/`HeroCard`/`ActionRow`/`TxnLine` 等共享组件。
- 现状视觉：品牌绿 `#1B6B4A`、浅色底 `#F4F7F5`、Material 卡片风 —— 与原型差异
  主要在**配色、字体、卡片质感、记一笔布局**，信息结构大体同构。
- 已有暗色主题（`values-night`）；原型明确「深色模式不在本轮」→ 与
  `ui-contract.md` 第 7 条「明暗两套验收」存在张力，需决策。
- `TxnEditScreen` 现状：可滚动、一级分类网格首格「不选分类」—— 与原型 v2.1 的
  「分类恒有值」「一屏零滚动」**有意偏离**（BASELINE v1.2 已登记，待确认）。

### 契约约束（`.trellis/spec/android/ui-contract.md`）

1. 只基于已确认原型版本（哈希核对）。
2. 范围不增不减：原型没画的现有功能保留；原型新能力不默认扩大范围。
3. 状态全覆盖：加载/空态/错误/重试/执行中/禁用/危险确认。
4. 单一设计来源：全部走 `core:designsystem`，`grep "Color(0x" feature/` 零命中。
5. 平台要求优先：insets、BackHandler、SAF、权限、无障碍 ≥48dp。
6. 验收不止编译：明暗两套、多屏宽、交互走查、与原型并排像素比对。

## Assumptions (temporary)

- 本轮为**视觉与交互改版**，不改业务逻辑、不改数据库（除单独确认的新能力）。
- 原型 v2.1 经用户确认后即为实现基准；实现期间原型冻结，发现不合理先改原型再确认。
- 分阶段交付，每阶段可独立构建、安装、验收。

## Decision (ADR-lite)

### D1：实现基准 = 原型 v2.1（已确认）

- **Context**：`ui-contract.md` 要求只基于已确认原型版本；v2.1 为最新版且此前待确认。
- **Decision**：用户于 2026-10-12 确认 v2.1 为当前实现基准；实现前哈希核对一致
  （index.html `8e667eb8…` / style.css `7fb9c0f4…` / app.js `fb8ddd32…`）。
- **Consequences**：`BASELINE.md` 已标记已确认；实现期间原型冻结，发现不合理先改原型重新确认；
  实现任务归档时引用本决策作为「哪个版本、谁确认」的答案。

### D2：记一笔两处偏离同步为原型口径（分类必选 + 一屏零滚动）

- **Context**：BASELINE v1.2 起登记真机与原型的两处有意偏离，待确认。
- **Decision**：用户于 2026-10-12 确认两处均同步原型：①取消「不选分类」首格，分类恒有值；
  ②编辑页一屏零滚动（分类区唯一可内部滚动，二级面板自动滚入视野）。
- **Consequences**：存量无分类账目展示时回退「其他」；AI 解析无分类时兑底「其他」；
  窄屏（360dp）与横屏需专项验收零滚动；`CategorySectionTest` 同步更新。

### D4：本轮锁定浅色，移除暗色跟随（用户确认的裁剪）

- **Context**：原型仅设计浅色；真机已有暗色主题；契约要求明暗两套验收且不得删现有能力。
- **Decision**：用户于 2026-10-12 确认本轮锁定浅色：全应用强制纸感浅色底，移除暗色跟随；
  暗色模式待后续单独出原型再实现。
- **Consequences**：这是契约第 2 条的**用户确认裁剪**，登记在案；验收时「明暗两套」
  条款对本轮豁免，改为「浅色多屏宽逐屏验收」；后续恢复暗色时需先补原型基准。

### D3：卡号进入本轮；schema 变更免迁移/免兼容（用户重新开始使用）

- **Context**：原型 v1.4 起账户可记录卡号；真机无 `cardNo` 字段。按 spec 改表需迁移+迁移测试，
  备份格式需兼容。
- **Decision**：用户于 2026-10-12 确认：①卡号能力进入本轮；②**不需要迁移与兼容**，
  用户从新开始使用，可接受破坏性变更（destructive migration / 直接重建 schema）。
- **Consequences**：升级安装会清空旧数据（用户已接受）；备份/导出格式可直接扩展卡号字段
  不写旧格式兼容分支；`database.md` 的迁移测试要求对本轮 schema 变更豁免（用户授权）；
  后续版本恢复「改表必迁移」纪律。

### D5：衬线字体采用混合方案（拉丁衬线打包 + 中文系统衬线回退）

- **Context**：原型要求金额/展示用衬线 + tabular-nums；Android 系统衬线对中文覆盖因设备而异。
- **Decision**：用户于 2026-10-12 确认混合方案：打包小体积拉丁衬线字体（含 tabular figures，
  如 Noto Serif Latin 子集，几百 KB）专用于金额/数字；中文标题类衬线走系统 `FontFamily.Serif`。
- **Consequences**：金额观感全设备一致（最关键场景）；APK 增量小；中文衬线在不同设备
  可能有细微差异（可接受）；字体资源入 `core:designsystem`，统一 Typography 定义。
